# AI 开发行为规范

## 1. 开始前必须做的事

1. 读取项目根目录的 `AGENTS.md` 和 `.agents/skills/prototype-management/SKILL.md`。
2. 确认本次需求 ID、需求名称和修改目标；没有明确 ID 时先确认归属，不要新建无归属页面。
3. 读取目标需求的 `requirement.json`、相关页面和 `components/`，先理解现有实现。
4. 查找可复用的公共组件和 Token；不要凭想象新建一套。
5. 用一句话说明本次范围：要改哪些文件、不改哪些文件、如何验证。

## 2. 修改边界

- 只修改目标需求目录内的文件和本次确实需要复用的 `src/components/` 公共组件。
- 不修改其他需求的页面、组件、Mock 数据或元数据。
- 不做与本次目标无关的重构、格式化、重命名、目录搬迁或依赖升级。
- 不新增依赖、不引入 Vue Router、不更换组件库、不改动 `vite.config.ts` 的 `base`，除非用户明确要求并确认影响。
- 不删除、重命名或移动已有原型文件，除非用户在当前对话中明确确认。
- 不为了“让页面显示”而删除其他页面、隐藏所有页面或硬编码导航。
- 不直接编辑 `dist/`；构建产物只由 `npm run build` 生成。
- 不向模板仓库提交、推送、打标签、建分支或 PR；不创建版本目录或变更日志。个人原型不进入版本管理。

## 3. 需要先向用户确认的情况

- 新增、删除或重命名需求目录、页面文件。
- 改变页面归属、跨需求移动页面、提升组件为公共组件。
- 改变主要业务流程、交互模型或页面结构。
- 新增第三方依赖、修改构建配置、引入路由或状态管理。
- 修改公共组件并影响两个及以上需求。
- 推送、发布、覆盖 PinMe 固定域名。
- 通过 MCP 写入 superPM 正式数据。
- 任何无法从现有代码和文档判断的业务规则。

确认时说明：改动对象、影响范围、替代方案和风险。不要用“应该没问题”代替确认。

## 4. 实现要求

- 使用 TypeScript 和 `<script setup lang="ts">`；不要用 `any` 绕过类型问题。
- 优先复用现有 `XlyButton`、FancyUI `Switch`、Element Plus 图标和 `src/components/` 公共组件。
- 新样式使用 `src/style.css` 的 Token；不要新增品牌色或自造间距体系。
- 需求专属组件放需求目录的 `components/`；公共组件放 `src/components/`，且不能依赖某个需求的 Mock 数据。
- Mock 数据留在需求目录内，确定、可重复，不使用真实令牌或客户信息。
- 保持现有外壳结构；不要重写 `App.vue`、`AppSidebar.vue`、`SystemSettings.vue` 的既有行为来迁就单个页面。
- 页面加载、空状态、错误状态和窄屏布局都要实现，不能只做桌面正常态。
- 代码注释只写非显而易见的约束；不要写大段说明或变更历史。

## 5. 完成前必须验证

- 运行 `npm run build`，确认 `vue-tsc` 和 Vite 构建都通过。
- 启动 `npm run dev`，在真实浏览器中打开页面，不只看代码。
- 检查：页面能从系统设置打开、导航高亮正确、主要交互可用、窄屏不溢出、控制台无报错。
- 如果改了显隐逻辑，验证隐藏当前页会回到系统设置、源码文件仍然存在。
- 如果改了公共组件，至少检查两个使用方。
- 如果无法完成某项验证，明确说明原因，不要声称已经通过。

## 6. 汇报格式

完成后按以下顺序汇报：

```text
需求：REQ-XXXX 需求名称
改动：新增/修改/删除的文件列表
行为：用户能看到什么变化
验证：构建结果 + 浏览器检查项 + 控制台结果
风险：未覆盖的场景、待确认事项
发布：未发布 / 已获得授权后发布（附地址与验证结果）
```

- 不要只贴代码或只说“已完成”。
- 不要隐瞒未通过的检查。
- 没有用户明确授权时，汇报结尾必须是“未发布”，不能自行执行 `npm run deploy`。

## 7. 禁止的捷径

- 关闭类型检查、删除报错页面、注释掉功能来让构建通过。
- 用 `localStorage` 或硬编码数组替换注册表的自动发现。
- 把所有页面塞进一个文件来规避归属规则。
- 复制其他需求的页面后只改标题。
- 未确认就删除“看起来没用”的组件或页面。
- 未授权就发布，或发布失败后声称成功。
- 直接操作 superPM 数据库、文件或 MCP 审计数据来绕过业务服务。
