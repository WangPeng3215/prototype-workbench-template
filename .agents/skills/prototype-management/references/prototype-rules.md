# 原型归属规范

## 1. 单一 Hub 模型

- 所有需求原型都在 `prototype-workbench` 一个项目内维护，不为单个需求新建独立子项目、独立 `package.json` 或独立构建配置。
- 一个需求对应 `src/prototypes/` 下的一个一级目录，这是该需求的唯一原型归属单元。
- 一个需求可以有多个页面；页面之间的文件、组件和 Mock 数据默认只属于该需求。
- 需求目录是导航分组，也是 AI 修改边界的判断依据。

## 2. 需求目录命名

```text
src/prototypes/REQ-XXXX 需求名称/
```

- `REQ-XXXX` 使用 superPM 需求 ID，四位补零，例如 `REQ-0001`。
- 目录名与 `requirement.json` 中的 `requirementId` 必须一致。
- 需求 ID 是不可变标识；修改展示名称时不要改 ID。
- 一个需求只建一个目录，不按阶段、版本或日期拆分目录。
- 目录名只用于展示和分组；分组顺序按名称排序，不要依赖目录数字前缀。

## 3. 需求元数据

每个需求目录必须包含 `requirement.json`：

```json
{
  "requirementId": "REQ-0001",
  "requirementName": "示例需求",
  "status": "in-progress",
  "summary": "示例需求原型的范围说明。",
  "owner": "示例负责人",
  "updatedAt": "2026-01-01"
}
```

字段约定：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `requirementId` | 是 | `REQ-XXXX`，与目录名一致 |
| `requirementName` | 是 | 需求展示名称，可与目录名不同 |
| `status` | 是 | `draft` / `in-progress` / `in-review` / `accepted` / `archived` |
| `summary` | 否 | 一句话说明该需求原型覆盖的范围 |
| `owner` | 否 | 当前负责人 |
| `updatedAt` | 是 | 最近一次修改日期，`YYYY-MM-DD` |

状态含义：

- `draft`：页面骨架或探索稿，尚不能评审。
- `in-progress`：正在开发，允许大幅调整。
- `in-review`：等待用户验收，非必要不再改结构。
- `accepted`：用户已验收；在系统设置中隐藏其页面，但保留全部代码。
- `archived`：不再维护；隐藏页面并保留代码，不删除目录。

`requirement.json` 目前不会被注册表读取，也不会自动改变导航；它用于 AI 和人工判断归属、状态与验收条件。保持内容真实，不要把它当作装饰文件。

## 4. 页面文件

- 页面放在需求目录内，命名 `NN-页面名称.vue`，例如 `01-原型库.vue`。
- 数字前缀只用于组内排序，不显示在菜单中；没有前缀的页面排在最后。
- 页面标题来自文件名。新增页面默认隐藏，需要在「系统设置」中打开。
- 新页面不得直接放在 `src/prototypes/` 根目录；根目录页面会被归入「页面」分组，无法判断需求归属。
- 页面 ID 由相对路径生成。重命名、移动页面会改变 ID 并使已有显隐状态失效，必须事先取得用户确认。
- 一个页面只负责一个主要场景；同一需求的复杂流程可以拆成多个页面，但不要为了拆分而复制整页代码。

## 5. 组件边界

### 需求专属组件

- 只被一个需求使用的组件放在：

```text
src/prototypes/REQ-XXXX 需求名称/components/
```

- `components` 目录不会被注册为页面。
- 需求专属组件可以包含该需求的业务字段、Mock 数据和交互假设。

### 公共组件

- 被两个及以上需求复用，或明确预期会被复用的通用组件放在 `src/components/`。
- 个人公共组件放在 `src/components/local/`；该目录已被 Git 忽略，不进入模板仓库。
- 公共组件必须与具体需求解耦：不导入某个需求的 Mock 数据、页面或专属组件，不硬编码需求 ID。
- 公共组件使用 props / emits 表达能力，类型放在 `src/types/` 或组件同目录。
- 不要提前把只被一个需求使用的组件提升为公共组件；等第二个需求真正需要时再提升，并同步修改引用。
- 应用外壳组件（`AppSidebar`、`SystemSettings`、`xly-button`）属于基础设施，不是需求原型组件，不要在需求页里复制或改写它们。

### 跨需求引用

- 允许：需求页引用 `src/components/` 的公共组件。
- 禁止：需求 A 直接导入需求 B 的页面、组件或 Mock 数据。
- 禁止：通过相对路径跨需求目录引用；需要共享时先提升为公共组件。

## 6. 验收、隐藏与删除

- 需求通过验收后，把 `requirement.json` 的 `status` 改为 `accepted`。
- 在「系统设置」中关闭该需求的全部页面开关；页面从导航消失，但源码、组件和元数据全部保留。
- 需要继续修改已验收需求时，把状态改回 `in-progress`，再打开对应页面开关。
- 不删除已验收或已归档需求的原型代码，除非用户在当前对话中明确要求删除。
- 删除、重命名、移动需求目录，删除页面，或用重写替代已有页面，都属于破坏性操作，必须先取得用户确认。
- 本项目不做版本管理：不要创建 `v1/`、`v2/`、`backup/`、`archive/` 等版本目录，不要写变更日志，不要向模板仓库提交或推送。

## 7. 新建需求原型流程

1. 确认 superPM 需求 ID、需求名称和本次页面范围。
2. 检查是否已存在同 ID 目录；存在则在其内追加页面，不新建第二个目录。
3. 创建需求目录和 `requirement.json`。
4. 创建页面文件；需要专属组件时放到需求目录的 `components/`。
5. 在「系统设置」中打开需要展示的页面。
6. 运行 `npm run build`，再启动开发服务器做真实交互检查。
7. 汇报新增/修改的文件、页面路径、验证结果和待确认事项。

## 8. 禁止事项

- 不为单个需求新建独立子项目或独立构建配置。
- 不在 `src/prototypes/` 根目录新增页面。
- 不跨需求导入页面、组件或 Mock 数据。
- 不删除或重命名已有原型而不确认。
- 不把 `requirement.json` 当作版本记录或变更日志。
- 不向模板仓库提交、推送、打标签、建分支或 PR；不创建版本目录。
